# CORE Tool Contract for PusingCuk

**Status:** CI integration proof implemented; production execution boundary not yet deployed.  
**Version:** 1 (CI proof; service execution remains gated)  
**Owner:** PusingCuk owns this contract's language-facing request/response shape; CORE owns authorization, persistence, limits and deployment.

## Goal and trust boundary

CORE may call a pinned PusingCuk runtime for a small, deterministic, reviewed computation. PusingCuk is experimental and is **not a security sandbox**. Do not run arbitrary user/model-generated source code in the normal CORE process or with the permissions of an API worker.

The first integration should execute only a registered program artifact with a reviewed hash and bounded inputs. It must not allow user-supplied code to choose arbitrary filesystem, network, database, process, environment-variable, or secret access.

## Ownership

- This repository owns the language version, program semantics, native/reference conformance fixtures and runtime build provenance.
- CORE owns the authenticated tool endpoint, user authorization, approved program registry, audit trail, business data access and execution evidence.
- MEMORY records the long-lived architecture decision and accepted rollout gates; it is not a mirror of request/response logs.
- PUBLIC must not expose internal tool requests, credentials, private source or operational evidence.

## Verified CI proof (2026-10-14)

The canonical pure rule is `examples/core/anggaran_threshold.cuk`. It classifies a nominal against a budget limit and returns one of `DALAM_BATAS`, `PERLU_PERSETUJUAN`, or `INPUT_TIDAK_VALID`. The native test target `make test-native` compares five deterministic cases against exact expected stdout.

CORE's `Core Quality Gate` pins this repository to a full commit SHA, builds the native runtime, runs the canonical example, and checks malformed input exits non-zero. This proves deterministic native execution in CI only. It does not prove that Supabase Edge Functions can spawn the native binary or that a production runner exists.

The runtime currently opens a source file and is not an OS sandbox. A production service must therefore be a separately isolated executor or a deliberately engineered WASI/runtime boundary. Do not bypass this requirement by executing arbitrary program text in an Edge Function.

## Local registered-rule runner

A local prototype service is available at `tools/core-rule-runner.mjs`. It:
- fetches/builds runtime source at the full pinned commit `23cc6b5b7d42ce5bc58babd37792a0ec32d117a8` unless an exact matching checkout is supplied;
- verifies the canonical `examples/core/anggaran_threshold_service.cuk` SHA-256 before serving requests;
- accepts only `budget.threshold.v1`, two bounded safe integers, an empty capability list, and a short request timeout;
- requires a random bearer token held by the runner process, bounds request/output sizes and concurrency, and passes a reduced environment to the native process;
- does not accept source code, arbitrary file paths, shell commands, database access, or model-provider credentials.

Start it locally with `PUSINGCUK_RUNNER_TOKEN="$(openssl rand -hex 32)" node tools/core-rule-runner.mjs`. The HTTP service binds to loopback by default. For a local Edge Function in a Docker container, use a private host bridge only if needed; never publish this endpoint to the public internet.

**This runner is still not an OS sandbox.** The native executable still runs as the operating-system user, so a reviewed fixed program and the language's current limitations reduce risk but do not establish OS isolation. It is a local development adapter only. Do not route production or arbitrary user/model source through it until an independently reviewed sandbox or isolated worker exists.

## Proposed request envelope

A CORE adapter sends a validated, versioned request to the PusingCuk execution boundary. It may use a registered artifact ID, not arbitrary shell text or arbitrary commands.

Required fields:
- contract_version: pusingcuk.core.tool.v1
- request_id: unique idempotency key generated by CORE
- program_id: allowlisted, registered program identifier
- program_sha256: SHA-256 pinned by CORE to the reviewed artifact
- language_version: exact language contract version
- entrypoint: registered operation name
- input: JSON object validated against that operation's input schema
- capabilities: explicit allowlist; empty by default
- limits: requested CPU/time, memory, input and output limits that CORE further caps

CORE must reject unsupported contract versions, unregistered program IDs, mismatched hashes, unknown capabilities, malformed JSON, oversized inputs, invalid schema, duplicate request IDs with conflicting payloads, and requests above configured limits.

## Proposed response envelope

The adapter returns:
- contract_version
- request_id
- program_id and program_sha256
- runtime_version and runtime_build_sha
- status: succeeded, rejected, failed, timed_out, or resource_limited
- result: JSON value only when succeeded
- diagnostics: structured error code, safe message, and source location when available
- elapsed_ms
- evidence_id or execution reference created by CORE

Never return credentials, environment variables, stack traces containing secrets, raw private context, or arbitrary file contents through diagnostics.

## Capability model

Default capabilities are denied. The first vertical slice should be pure/deterministic and should not require external capabilities.

Potential future capabilities must be independently versioned, allowlisted and authorized by CORE, for example:
- core.research.read — read a safe, bounded projection through CORE
- core.evidence.read — read a safe, bounded evidence reference through CORE
- core.validation.run — run a registered validation rule against an explicitly supplied input

Do not enable general-purpose core.db.write, arbitrary HTTP, filesystem access, process spawning, environment reads, model-provider credentials, Supabase service_role access, or secret reads. If a future business operation needs a write, expose a separately authorized CORE business operation; never hand the database credential to the interpreter.

## Authentication, idempotency and audit

- Authenticate the caller at the CORE boundary using an approved Supabase/JWT or server-to-server authentication path.
- Verify identity and permissions server-side. Do not trust a model-supplied actor ID.
- Do not pass the bearer credential, API key, service-role key, or other secret to the interpreted program.
- Use request_id as an idempotency key; record request metadata, artifact hash, runtime/build, allowed capabilities, status, elapsed time and evidence reference in CORE.
- Redact input fields classified as sensitive before logging.
- Return a stable error code to callers; preserve detailed diagnostics only in restricted CORE logs.

## Limits and isolation

PusingCuk currently does not provide a security sandbox. Until an audited isolation mechanism and threat-model tests exist:
- run only trusted, reviewed, pinned program artifacts;
- execute in a disposable isolated worker with no ambient secrets and no network/filesystem capability;
- enforce server-side time, memory, input and output ceilings;
- terminate the worker on timeout or resource violation;
- keep the database and auth authority outside the runtime;
- do not route arbitrary public source text into the runtime.

Numerical ceilings must be set from CI/staging benchmarks and documented with the runtime version; a configurable timeout alone is not a sandbox.

## Error taxonomy

- INVALID_CONTRACT
- UNKNOWN_PROGRAM
- ARTIFACT_HASH_MISMATCH
- INVALID_INPUT
- CAPABILITY_DENIED
- UNAUTHORIZED
- RESOURCE_LIMIT
- TIMEOUT
- RUNTIME_ERROR
- INTERNAL_ERROR

Error responses must not contain a secret, private prompt/context, or raw privileged database payload.

## Acceptance gates

1. PusingCuk conformance tests pass on the exact pinned commit.
2. The registered program has deterministic fixtures for valid and invalid inputs.
3. A CORE contract test checks schema validation, auth, capabilities, idempotency, timeout and output bounds.
4. Runtime tests demonstrate that filesystem, network, subprocess, environment and secrets are not available to the program.
5. CORE stores an audit/evidence reference without duplicating the program or result payload across repositories.
6. One small pure business-rule integration passes end-to-end in staging.
7. A rollback path can disable the tool route without removing or rewriting existing CORE records.

Until all gates pass, the contract is a proposal and the production integration status remains **not verified**.
